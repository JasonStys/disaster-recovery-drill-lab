# Operating and recovery runbook

Author: Jason Stys. Use only owned synthetic native tests or a dedicated disposable Linux Docker host.

## First use and help

Follow the README five-minute native setup. Bootstrap verifies official archive hashes before extracting a regular executable; no shell installer executes. Native tests and offline objective example do not call Docker. Pick a new out/name each time; preserve prior evidence. View only selected report HTML locally.

Before database exercise, review its synthetic schema and explicit lab objectives. Acknowledge the dedicated host flag; no existing database, remote Docker context, host port or real customer data can be targeted. The source gets 40 settled orders; original commit timestamps are persisted before custom dump/encrypted backup. Five later committed orders demonstrate nonzero loss. Source stop begins RTO; isolated decrypt/start/transactional restore, read/money/constraint checks end it.

Reports require all cases, exact source/snapshot/dump hashes, database consistency and explicit budgets. Losing five orders can meet the configured demonstration objective but is NOT a recommendation that a business should accept that loss. Check original resumes/business requirements separately before adapting any operational objective.

## Failure handling

- Offline exit 2: malformed/duplicate/oversized/deep/non-UTF8 input, unknown schema/type, ordinary-file or new-output violation. Error text is fixed, not a raw-input echo.
- Offline FAIL/exit 1: valid observation did not meet original snapshot or configured budget. Keep the result; do not silently widen limits.
- Native wrong-key/missing-ID/corruption case: require its specific oracle. Generic permissions/network/process errors cannot pass as successful defenses.
- PostgreSQL failed_stage: public diagnostic gives the fixed stage, not env/passwords or raw inspection. Private ignored output remains for authorized local inspection. Use actual job step failure and only the owned names; never paste full container inspect/env-files/backups into GitHub.
- Readiness: temporary initdb PostgreSQL can answer readiness before final initialization. The program requires PID 1 postgres plus current database and commit tracking. Do not bypass that guard.
- Constraint/archive mismatch: preserve baseline fingerprints and exact snapshot/dump ID. Never use latest or restore over an existing destination. Untrusted pg_restore input can execute SQL; do not import arbitrary uploads here.
- Image/dependency/security advisory: verify/update appropriate official pinned source and repeat all checks. No suppression for a green badge.

## Cleanup and recovery boundaries

Normal/failure cleanup stops/removes only names created and labeled by this run after exact ownership/isolation verification. No broad Docker prune, volume deletion or unrelated process kill is used. Hard host termination can interrupt cleanup: inspect the exact dr-lab run label/names first, and remove ONLY verified owned containers with separate explicit authority. Do not delete user data or old Actions runs.

Ignored out/ contains plaintext synthetic dumps and generated synthetic passwords as well as encrypted repositories. Keep it private; backup encryption is not blanket working-directory encryption. The lab does not require real keys, data, secrets, hosting or system-security changes. Windows user ACLs/admin remain the local boundary. Delete selected disposable outputs only when authorized and no longer needed.
